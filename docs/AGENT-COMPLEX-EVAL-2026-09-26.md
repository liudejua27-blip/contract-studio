## 测试范围与配置

使用当前配置的 `deepseek-flash`、开启思考、`high` 强度，单次输出上限 8000，现有任务预算与自动重试策略均保持原样。生产 Agent 源码哈希与测试前清单逐项比对一致，没有边测边改提示词或放宽校验来提高通过率。交易与材料全部为合成数据。

执行真实 Pi SDK、实际工具、材料解析、交易状态和后台工作流逻辑；持久化使用独立本地文件及内存版本检查，没有操作真实客户账户或数据库。本轮没有浏览器交互、生产部署、律师审定或容量验收。法律检索未配置，且各例尚未运行到计划的法律边界问答。

三个任务预先固定输入和评审标准：

1. **三方软硬件一体化交付**：三方名称留空；180000 元总价分为软件 120000 元、硬件 60000 元；分别付款、接口依赖、联合验收、维护起算、知识产权、迟延责任。计划再做只读解释及一次关联日期修改。
2. **报价冲突与内容授权**：DOCX 报价、TXT 会议记录及参考范本；先发现总价、交付物和版权冲突，再由用户明确选择。计划将六条成片改为八条，并同步调整总价及三期期款，同时保持有限授权。
3. **四方活动收入分成**：场地票务、运营、作品授权、设备四方分工；固定运营费与浮动分成分开；限定扣费项目、无保底收益。计划连续修改人数上限和分成比例，检查前一轮更正是否保留。

输入与标准见 `scripts/complex-agent-cases.ts`。这些用例没有提供预期模型输出。失败后没有人工替 Agent 改写事实，也没有手动重跑以挑选成功结果；计入系统内置的全部自动重试。

## 关键发现

### 1. 输出额度与复杂任务不匹配，失败恢复又重复原请求

32 次调用中有 **19 次 `AI_OUTPUT_TRUNCATED`**，全部三个任务最终停在这个错误。截断调用共消耗 **152001 个输出 Token，占总输出 73.38%**；对应模型费估算约 **¥0.6613–0.9209**，未形成可提交的阶段结果。该金额是这些调用的实际用量估价，不是已经验证的可节省金额。

材料任务有一次回复报告输出 8001 Token，其中思考 Token 同样为 8001，未留下可用的结果。当前模型在思考模式下使用统一的 8000 输出配额；[官方 API 文档](https://api-docs.deepseek.com/zh-cn/api/create-chat-completion/)将思考 Token 列入 completion 用量详情，且思考模式默认输出额度更高。当前上限是应用主动设定，不是模型只支持 8000。

`src/server/agent/transport.ts:35–49` 在截断后以同一配额自动重试一次；`src/server/workflow.ts:127–132` 又把截断归为临时故障，再从阶段重试。三方任务第二轮和材料任务第二轮都因此连续产生 6 次截断。界面活动提示还把这种情况说成“临时连接问题”，与真实原因不符。

**优先优化**：按任务及阶段分配输出/思考额度；在总预算内对截断做一次有明确变化的恢复，例如扩大输出额度或缩小本轮结构化更新。反复相同截断应停止，并给出准确、可恢复的状态。仅把所有任务的预算无条件调大，仍可能保留重复消耗。

### 2. 原文、事实、事项判断和交易关系之间的重复引用造成多轮修复

三方第一轮 `update_contract_spec` 提交 5 次才接受；材料第一轮提交 4 次才接受，累计记录 7 次工具校验失败。错误包括诉求引用不匹配、材料页段引用不匹配、关系引用没有出现在对应事实证据中，以及事项判断引用没有同时保存在 facts 中。

部分检查有必要：不能把参考范本当真实承诺，也不能伪造来源。但目前模型需要在 `facts.quote/evidence`、`businessChecks.evidence`、`relationUpdates.quote` 等多个位置重复维护同一原文，关联或复制出错就需要重新提交大型结构。材料来源引用遗漏后，反馈还会转向查找用户口述原文，增加修复难度。

**优先优化**：用服务器提供的来源编号、页段或文本区间关联证据，让模型选依据、表达交易关系；确定性部分由代码完成。保留防编造、角色和权限边界，同时减少重复复制及一处失误导致整轮重写。事实台账可支持经校验的局部更新，但只在完整交易就绪时供用户确认，不增加新的用户审批步骤。

### 3. 长会话保存了连续性，也积累了大量重复结构

材料任务首轮请求为 8585 输入 Token，第二轮已达 46392；第二轮每次重试重复发送相同规模的上下文。该用例每次工具定义本身为 13050 字节。原话、模型先前提交的结构、错误反馈和当前台账共同进入后续上下文。

**优化方向**：按阶段提供需要的工具和字段；保留当前事实、来源索引、未决事项与最新变化，旧的失败结构按需查阅。会话恢复仍应保留，但不必把每次失败的完整结构长期作为活跃上下文。效果要用“完整任务成本与等待时间”衡量，不能只看单次调用少了多少 Token。

### 4. 当前监控需要从请求成功扩展到业务任务成功

模型成功返回工具调用时，调用记录可以是 `ok`，但工具校验仍可能失败。本轮最终全部失败，却有 13 次调用标为 `ok`。现有线上 `ModelCall` 仅保存总输入/输出，也没有缓存及思考拆分。

**优化方向**：分别记录网络/模型请求结果、工具校验结果、阶段结果及整份合同任务结果；保留缓存命中、思考用量、重试原因和从首次输入到可下载版本的时间。运营指标优先看完成率、每份成功合同成本、用户等待和重试放大倍数。

## 从整个 Agent 看

已经看到的能力：三方角色分离、姓名留空、六条交易关系；实际读取 DOCX/TXT；识别价格、交付范围和版权三类真实材料差异；失败时保留用户消息和上一轮摘要。底层任务与来源机制并非空壳。

尚未证明的能力：复杂信息补全后稳定形成确认记录、复杂初稿生成、全篇和附件关联一致性、只读问答以及连续两轮修改。本轮没有成稿，不能评价法律专业质量，也不能验证 95% 目标。

**当前最该做的是提高从“已理解一部分”到“完成用户任务”的可靠性。** 优先顺序建议为：

1. 修复输出额度与截断恢复，准确呈现失败原因。
2. 简化来源与事实更新协议，减少重复引用和整轮重做。
3. 整理阶段上下文，完善整任务的质量与费用记录。
4. 继续使用这三个冻结用例验证改善；它们此后属于开发回归样本，真实质量验收另用未参与调优的样本。

本轮证据不支持优先更换 OpenAI Agents SDK 或增加更多 Agent。当前瓶颈位于应用的输出配额、结构化交互和失败恢复；框架迁移不能直接消除这些问题。调整后是否需要更换模型，仍应通过相同任务的受控对比来判断。
