# 合同 Agent：收拢职责与质量验证

本轮仅完成本地实现、构建和测试，未部署。产品仍是完整 Pi SDK 驱动的通用合同 Agent：理解真实交易 → 通用起草 → 按需专项增强 → Word 初稿 → 律师审核。没有新增外部法律服务或第二套 Agent。

## 实现

- 沟通、摘要确认、直接起草和导出统一使用 `transaction-state` 的缺项判断。模型的 `businessChecks` 负责商业完整性；固定字段只作保守兜底，不再叠加关键词场景问卷。旧 `questions/materialGaps` 仅在输入边界转换，新的工具结构不再暴露它们。
- 已回答、缺失、暂未决定和不适用有明确状态。跨字段证据可以回答同一事项；不适用须有原话和原因。自定义商业事项与旧未决事项可以保留，多方和混合交易继续支持。辅助签署资料不阻塞起草。
- 接受建议后保存其来源；未接受建议不能成为事实。明确未定的证据不能又被当成问题重复提问。后续在其他字段回答后，清除对应的待沟通状态及旧律师提醒。
- 保留模型对本轮补充的自然回应，再显示统一判断产生的最多三个问题。自定义事项可带中文名称，界面不再直接暴露其内部字段名。
- 通用起草 Skill 升至 4.0.0；Word Skill 保留 3.0.0。通用 Skill 负责交易和质量方法，系统提示负责身份与沟通，工具负责结构和交付。删除重复适配提示、取消规则引用最低数量；完整通用参考改为按需读取，相关专项仍可组合载入。
- 工具参数从现有 Zod 验证结构生成 JSON Schema，金额、数组、文档块等结构直接提供给模型。运行时继续检查实际数据和事实来源；未知扩展字段按原有 Zod 规则剥离，不成为可信业务数据。
- 保留证据中的所有原话片段，修复“证据已保存，但只检查展示值导致反复重试”的问题。无偿的明确表述可通过金额检查，不能被改写成收费合同。
- 空参数的可选规则查询可正常执行；不完整工具 JSON 在执行前最多恢复一次，未通过验证不会提交结果。保持已有会话隔离、任务恢复、版本和文件保存确认。

## 本地验证

- 自动检查：141 项，其中 137 项通过，4 项依赖数据库环境的集成检查跳过。新增 15 项状态、工具、证据及入口回归检查。
- Node 生产构建、Sites 兼容构建、Sites 类型检查和 Node 类型检查通过。Sites 构建仅代表兼容产物，未把线上服务切换到完整 SDK。
- 通用 Skill 格式检查通过。
- 软件合同真实模型测试：80000 元改为 90000 元后起草、核对、生成真实 Word；检查了付款表格、主体邮箱、乙方授权签署人、签署方式及旧金额不残留。相关 Word 来自实际生成，最后一次脚本复测复用了已验证草稿，仅重跑退款未定的沟通场景，并非重新生成整份合同。
- 20 个合成业务案例覆盖软件、采购、服务、无偿、保密、租赁、设备借用、视频、三方合作、自然人、退款、否定、改口、未知合同及建议。最终整批原始自动评分为 19/20：唯一被判失败的运维案例实际上分别追问了运维范围、期限、费用，评分器却只接受名为 `maintenance` 的单一字段。保留原始记录，按实际商业含义修正评分器并重评全部记录后为 20/20，未重新调用模型挑选答案。
- 该批场景完成耗时中位数约 10.4 秒，最长约 38.9 秒；首次可见内容中位数约 1.3 秒。部分案例含两轮对话；这些数据是沟通整理的本地观测，不是完整合同生成时延承诺。
- 软件场景 Skill 注入文本：起草由此前约 18054 字符降至 8793 字符，核对由约 21460 字符降至 8767 字符。仅统计 Skill 包，不代表整个请求上下文大小。

## 尚需真实验收

这些案例是合成数据，20 个案例主要评估沟通与事实状态，并非 20 份完整合同的律师评审。真人律师尚未填评审表；实质条款遗漏、法律适用和必要修改量仍需律师盲评。模型可能需要内部修正，不能保证所有表述永不重复询问，也不能将此轮通过视为线上稳定性承诺。

本轮没有改造整份合同的自动重写为局部编辑，也没有训练模型或自动学习律师修改。保持现有有界修复与人工审核流程；下一步应先让律师评阅这些真实导出结果，再根据明确问题迭代。
