# 合同文件格式、内容与签署交付核查

核查日期：2026-09-21。范围：官方示范文本、GitHub 上游能力、当前本地代码和既有合成交易样本。本次是审阅，未修改应用代码，未部署，未进行真人律师法律审查。

## 判断

当前 Agent 已具有交易起草、事实确认、动态条款与附件、真实 Word 导出和律师版本交接能力；仍不能把“生成 Word 成功”等同于“形成可签署的专业合同”。主要缺口在主体与签署建模、履约细节、丰富文档结构和实际排版验证。

A4、宋体、小四和行距是可采用的产品排版规范，不能称为所有中国合同统一的法定有效要件。民法典第 470 条列举合同一般内容；第 490 条规定合同书形式下的成立规则。特殊合同另有要求。官方示范文本也需要结合交易修改，不能把空白表单直接作为已完成合同。

## 建议采用的合同文档规范

| 部位 | 产品默认值或处理方式 |
| --- | --- |
| 纸张 | A4，210 × 297 mm，纵向；特殊清单可按需横向 |
| 边距 | 上下 2.54 cm，左右 2.5–3.17 cm；根据装订方式配置 |
| 标题 | 居中、16–18 pt、加粗；合同名称来自真实交易 |
| 正文 | 宋体 12 pt，1.5 倍行距；数字与西文设明确字体 |
| 层级 | 连续条号，支持条、款、项；引用能随修订核对 |
| 表格 | 采购明细、费用计划、交割单用真实 Word 表格；表头重复、行跨页控制 |
| 页眉页脚 | 合同简称、适用时显示编号；第 X 页 / 共 Y 页作为产品规范 |
| 签署区 | 按企业、自然人、代理签署及多方角色生成；预留足够签字盖章空间 |
| 附件 | 实际存在、名称和编号对应正文；交割确认类附件按业务需要独立签署 |
| 质量检查 | 文件可打开之外，检查字体、分页、表格溢出、空白页、签署区和附件完整性 |

示范文本的官方封面、发布机关和 GF 编号不能复制成平台自行起草合同的官方背书。长合同可有封面、目录，短合同不强制增加。

## 应填写哪些信息，以及何时获取

- **起草时必须明确的交易事实**：交易各方和角色、合作事项、数量或范围、费用或其他交换安排、付款条件、时间、交付与验收安排；只询问当前交易实质缺失的部分。
- **签署前按场景补齐的客观资料**：主体全称、主体类型、住所、适用的统一社会信用代码或证件资料、联系方式、实际签署人及授权身份、必要的收款账户。并非所有合同都必须列身份证号、银行账户或邮编；只收必要资料，不由 AI 编造。
- **系统起草并交律师判断的事项**：法律措辞、争议解决、责任边界等。涉及交易实质利益的事实，例如退款如何影响分成、谁承担运费，不能全部转给律师替当事人决定。
- **签署时才形成的信息**：实际签名、盖章、签署日期。留出签署空白与遗漏交易事实不同，不能为追求“无占位符”预填虚假签署信息。

维持“先下载 AI 初稿，再律师审查”的产品流程。将“可起草”“可送审”“签署资料齐备”区分，不能用一套必填项阻止用户先形成初稿。

## 当前缺点及代码证据

### 1. 主体结构过于简化，多方合同被硬限制

`src/lib/types.ts:5` 的主体只有 role/name/details，主体类型、代表人、代理关系、送达联系方式等没有专用结构；可以写入 details，但不便可靠校验和按类型排版。

`src/lib/contract-library/playbooks.ts:30` 要求 `parties.length === 2`。诊断复现：在完整测试合同增加丙方后，得到 `双方名称不完整`。这是当前能力范围限制；不能宣称支持任意多方合同。

### 2. 签署数据没有完整进入交付文件

`src/server/documents.ts:342` 统一生成“角色 / 名称及签字盖章 / 日期”的三列表格，无企业与个人区分、无授权签署人字段、无明确盖章留白尺寸。

`ContractContent.signing` 虽存在，但 `renderContract` 没有读取它。诊断复现：传入签署地点与授权代表后，导出的文本不含二者。当前起草提示词通常要求 signing 为空，因此这是数据模型与渲染脱节，不能据此断言所有线上合同已丢失签署信息。

`playbooks.ts:21` 和起草提示词固定使用“双方签字盖章后生效”，没有按主体和签署约定选择表达。应由律师审定签署方案，并让生效条款与签署区对应；不应简单将所有合同批量替换成另一个统一说法。

### 3. 排版配置未针对中国合同形成稳定规范

`src/server/documents.ts:444` 使用 Letter（215.9 × 279.4 mm）；正文 11 pt，行距值 320（自动行距下约 1.33 倍），页边距约 2.12 cm。都不是合同当然无效的理由，但与本产品拟采用的 A4、小四、1.5 倍规范不一致。

已有标题、页眉、当前页码、一级条号、附件和签署分页。缺少总页数、丰富层级、表格跨页规则和适配签署区。`keepNext` 已用于条款标题，不应误报为完全没有分页控制。

### 4. 正文和附件缺少真实表格能力

`sections`、`attachments` 都只有 title/content 字符串；生成器按换行输出段落。现有 Table 仅用于固定签署区。采购报价、分期付款、租赁交割、设备清单需要表格或清单节点；提示词要求“排得专业”不能解决结构能力缺失。

### 5. 事实一致性检查还不足以保证履约细节完整

检查了既有合成交易产物 `.data/qa/transaction-skills-1789999384890/draft.json`：咖啡机、门店软件、收入分成混合交易。优点是保留 60%/40%、不扣成本、合作期限、设备归属、不交源码和终止数据交接顺序。

仍缺谁统一收款、谁向谁付款、退款与折扣如何进入分成口径等实际结算安排。“每月月底核对并结算”未完全覆盖这些操作事实。reviewNotes 把收入口径交给律师，但其中部分应向用户用生意语言确认，或呈现明确方案供确认。

一次可以只问：“顾客的钱先收进谁的账户？退款要从当月收入里扣掉吗？” 不需要用户理解法律概念，也不能默认增加付款比例或免除责任。

### 6. 已接入 Skill，但未接入上游 Word 工程规范

当前 `src/server/agent/legal-skills.ts` 载入通用交易、独立起草、语言规则、专项参考和平台 `contract-word`。平台 Word Skill 主要是文字约束，具体排版仍由固定渲染器完成。

上游已有 `contract_standard.json`：A4、12 pt 正文、1.5 倍行距；并提供导出后实际 DOCX 字体、字号、行距、页码和表格检查。建议移植必要规范到现有 Node/Sites 生成器，不必整体搬入桌面 Python 流程或更换 Pi。

当前 Skill 审计能核对规则引文和合同文字的位置；`located` 不代表规则适用正确、所有相关规则已覆盖或合同可签署。

### 7. 导出测试偏结构，视觉验收还不够

现有测试检查真实 OOXML、页眉页码、附件和单一签署区等，有价值，但不能证明打印出来的布局良好。需要增加多方、长公司名、多页表格、长附件、自然人签署等页面样本。

本次把既有合成 DOCX 转成检查用 PDF 时，转换环境出现中文缺字方框。故不能用该 PDF 判断源 Word 在 Word/WPS 中的最终视觉质量，更不能误报源文件本身乱码。已有浏览器预览截图可显示中文；应补充中文字体完整的转换环境与 Word/WPS 渲染验收。

## 建议实施次序

1. 先修主体与签署数据：主体类型、代理关系、多方支持、签署字段实际落入 Word；保留历史版本兼容。
2. 同轮升级 Word：A4 排版配置、真实表格与多级条款、签署留白、附件引用与实际页面检查。
3. 补交易可执行性追问：付款路径、结算口径、交接与退出操作；系统法律默认条款与真实商业决策继续分离。
4. 以企业间、企业与个人、三方、无偿、混合经营、长清单六类合成交易回归，再由律师抽查最终 Word。测试通过、律师审定和部署分别记录。

无需为解决这些问题更换 Pi SDK，也无需接入企业查询或付费法律数据库；先把当前文档模型、渲染器与交付检查补齐。
