# 合同 Agent：一份交易记录，一次提交

本轮仅修改和验证本地项目，未部署。保留完整 Pi SDK、Flash Thinking high、通用起草 Skill、按需专项规则、Word 和律师审核流程。

## 核心问题与调整

原 collectIntake 在工具提交时构造临时记录做检查，提交成功后又重新合并事实，执行关键词判断和付款识别。检查对象与保存对象不同，模型理解正确也可能被后处理删掉。各模板还有各自的必填清单，切换类型会增加问题。

现在由 `src/lib/transaction-update.ts` 一次构造并验证当前交易记录。`collectIntake` 返回工具验证过的同一个结果，不再重新抽取或增删事实。已接受建议、普通模型更新共用这个入口。修改中的临时记录与已保存记录隔离；失败不会覆盖先前记录。

- 新交易记录的必要要点来自实际交易：参与方、合作内容、费用或交换及结算、履行时间。允许跨字段证据、无偿与非金钱交换。专项类型只帮助找到参考规则，不决定另一份必填问卷。
- 缺少内部字段判断时先向 Pi 返回修复反馈。日期在 delivery 中，不等于用户没说 term。上一轮的缺项需重新判断，避免原样重复旧问题。
- 删除按“几次付款／几个元或百分比”删除付款字段、按独立付款句式强行覆盖模型结果、按源码关键词补另一个必填字段的后处理。分两次付款这个已知事实可以保留，同时只问比例或节点中真正缺少的部分。
- 自然语言明确接受已存在建议，由 Pi 返回建议标识；不再要求某个固定口令。用户本轮明确给出的安排优先于旧建议，不能被建议文字覆盖。未接受的建议不能自动变成事实。
- 金额检查与交易判断使用相同的有依据记录。无偿判断不能因解析器没认出某种表述而变成价格追问；明确金额、分期合计与真实矛盾仍检查。
- 数字检查不通过时先让 Pi 判断是否因抽取混入总价、旧报价造成。修复引用问题后再决定是否存在用户需要回答的真实矛盾。
- 证据错误返回具体缺失片段和修复位置，避免笼统错误造成反复重试；保留原话校验、律师事项、确认绑定、文件保存和审核版本检查。
- 原已确认旧版本保留原来的检查口径；继续聊天产生的新记录使用新口径。不会批量改写已交付合同。

通用起草 Skill 升为 4.2.0，删除应用层重复的长篇访谈提示。Skill 明确当前有效证据、跨消息改口、只问重要事实，以及已约定范围外的未来新增工作另行确认，不提前追问假设情形。没有增加外部法律服务或第二套 Agent。

## 验证原则

自动检查验证状态、金额、工具修复和交付约束。真实模型评估使用合成交易，评估的是沟通与事实处理，不代表律师认可合同法律质量。完整 HTTP 流程使用隔离数据库、测试存储、合成客户与模拟律师账号；没有联系真人律师。

旧测试中依赖模板强制字段或关键词自动改写的模拟模型响应，已改为显式的交易判断。保留未知事实、金额冲突、否定、撤回、无偿、新增费用和虚构证据的负向检查。

## 迭代中实际发现的问题

1. 首批口语案例中，交货日期已保存在 delivery，缺少 term 判断时仍产生了重复问题；现改为工具内部补齐判断。
2. 无偿借用的原话不是固定句式，被数值解析器误判；现在共享已有证据支持的无偿判断，并继续禁止导出时新增收费。
3. 金额矛盾案例的修复反馈过于笼统，模型重复调整事实和证据；现在反馈具体未保存片段，定向复测成功。
4. 改价案例把总价计入分期，并把旧报价拼进最新事实；增加内部复核及当前有效证据规则。新增回归模拟同样错误，证明先内部修复、再发布结果，不把错误先交给用户。
5. 装修案例实际问了材料由谁采购，评分器却只接受名为 materials 的字段。评分现在核对问题含义；原始失败报告保留。
6. 设计案例多问约定次数之外的额外修改，已增加普遍的范围边界原则，并加入对应的禁止无关追问评估。
7. 软件三轮案例最终通过，但旧建议覆盖本轮明确付款答案，且建议标题总价被计入期款，导致多次内部修复。现以本轮原话为准，并区分分期标题总额与各期款项；增加两种路径的回归检查。
