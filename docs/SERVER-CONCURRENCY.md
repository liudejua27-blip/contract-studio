# Node 服务器并发与按需扩容

本次升级使用完整 Pi SDK、现有 PostgreSQL 和私有 S3。仓库已移除 Sites 兼容层，默认构建即服务器版。以下是交付的代码和操作方式，不代表已部署或已通过真实模型的 100 用户压力验收。

## 运行结构

用户提交 → PostgreSQL 保存任务 → 后台领取阶段 → 异步调用模型 → 保存共享会话检查点 → 核对 → S3 保存 Word → 数据库发布版本。网页只提交、订阅结果；在 external 模式下不执行模型任务。

每个任务阶段需要数据库中的全站执行名额。所有进程以同一个数据库策略为准，领取名额和选择任务在短事务中完成。模型调用和文件上传不持有数据库事务。一个合同同一时刻只能被一个执行者领取；不同合同可以同时运行。

- 默认每进程 30 个执行名额，全站 120 个。阶段内部的模型工具循环仍按依赖顺序执行。
- 全站为需求问答保留 20 个名额，长时间起草、核对、导出最多占 100 个。各进程也按比例保留问答名额；保留名额在没有问答时允许空闲，优先保障交互响应。
- 独立监督进程每 5 秒看一次任务量，在 1–4 个后台进程间自动扩缩。增长时补充进程，空闲持续 60 秒后逐个减少，减少时等待当前阶段完成。
- PostgreSQL 中有每合同的 30 秒执行名额租约，执行进程每 10 秒批量续约。工作流还保留自己的阶段租约和重试预算。进程意外消失后，等待相应租约到期再接管；这可能需要数分钟，不承诺立即恢复。
- 过期执行者不能提交新合同状态、覆盖共享会话或删除替代者的名额。取消任务会停止后续提交，模型请求在定期检查时中止。
- 模型返回 429 时采用 Retry-After（缺失则 30 秒，最长 10 分钟）暂停全站新模型任务，已完成内容仍允许导出 Word；自动重试次数有界并加随机错峰。
- 默认全站最多接受 1000 个活动任务（排队和运行合计），单账户最多 1 个、每小时 40 次请求。超量会拒绝新请求并保留网页输入，不会无界积压。
- 进度订阅约每秒更新，同一进程内相近的订阅合并为批量数据库读取。用户会看到排队状态，重连恢复已保存的正文。

## 构建和启动

使用 Node 22，先准备 PostgreSQL、私有 S3，以及模型与会话密钥。构建环境安装完整依赖；构建产物的 worker 运行不需要 tsx 或 esbuild。生产运行仍需要 package.json 的 dependencies。

```sh
npm ci
npm run build
# 本地使用 .env.local；生产先将受控环境文件注入进程，再运行同一初始化脚本。
npm run db:init
```

初始化在原表上增加任务调度、共享会话检查点表，不删除已有合同和版本。先备份生产数据库再迁移；滚动升级前要停止旧版内嵌执行者，因为旧代码不遵循新全站名额。迁移完成后再启动新网页和后台进程。

生产环境设置 `CONTRACT_WORKER_MODE=external`。在两个受进程管理器管理的服务中分别运行：

```sh
npm run start
npm run workers:autoscale
```

`npm run worker` 则只启动一个独立执行进程，供容器副本或其他进程管理器控制数量。开发默认 `embedded`，网页进程同时执行后台任务；这一模式不会自行创建更多进程。

`ops/systemd/` 提供两个服务模板，假定代码位于 `/opt/contract-studio`、受控环境文件位于 `/etc/contract-studio/server.env`。按实际机器修改 Node/npm 路径并创建专用系统用户。网页仍监听本机 3210，通过现有 HTTPS 反向代理对外提供服务。模板仅交付，未安装、启动或开放端口。

## 设置并发与扩容范围

| 设置 | 默认 | 生效位置 |
| --- | --- | --- |
| CONTRACT_WORKER_CONCURRENCY | 30 | 每个后台进程，重启生效 |
| CONTRACT_AI_GLOBAL_CONCURRENCY | 120 | 全站总上限，写入数据库策略 |
| CONTRACT_AI_INTAKE_RESERVE | 20 | 全站问答保留名额，须小于总上限 |
| CONTRACT_AI_MAX_QUEUED | 1000 | 全站排队和执行中的合同总量 |
| CONTRACT_WORKERS_MIN / MAX | 1 / 4 | 每个监督进程允许的后台进程数 |
| CONTRACT_AUTOSCALE_INTERVAL_MS | 5000 | 扩缩判断间隔 |
| CONTRACT_AUTOSCALE_COOLDOWN_MS | 60000 | 缩容前的持续低负载时间 |
| CONTRACT_WORKER_SHUTDOWN_MS | 660000 | 优雅退出最长等待，之后强制终止 |

全站策略只在初次初始化时采用环境变量，后续不会被另一个实例的旧环境覆盖。修改这三项全站设置后，由受信任的服务器操作人员执行：

```sh
npm run workers:configure
npm run workers:status
```

缩小上限不强杀已有任务，而是停止超限的新领取并逐渐降到目标。仅在某个进程修改环境变量不会改变全站策略。

当前默认按 100 个合同阶段同时执行设计：4 个后台进程，每进程 25 个长任务名额，另有每进程 5 个需求问答名额。监督进程按任务量自动增长到这个规模。这是代码容量目标；遵照用户要求，没有完成或重跑 100 用户负载验收，也没有发起真实模型压力测试。

多服务器可运行相同后台程序，共享 PostgreSQL、私有 S3 和一致的模型配置；总上限不会随服务器数量倍增。Pi 会话原文保存在私有数据库检查点，临时 SDK 文件每阶段结束即删除，不需要共享服务器磁盘。升级前旧本地会话在原机器第一次使用时自动导入；迁移机器前应先导入或安全搬迁旧会话目录，避免只剩公开对话而丢失旧内部检查点。

自动扩缩的是已有服务器上的后台进程，本次没有对接云厂商购买/销毁虚拟机。跨主机自动扩容可以使用现有容器编排平台读取任务指标，启动更多同款 worker；共享数据库继续限制总并发。无需通过多 API Key 绕过供应商账号限额。

## 观察与验收

`GET /api/operations/generation` 仅管理员可访问，返回任务待处理数、可领取数、运行数、当前失败数、最老排队时间、持有名额的实例数及数据库策略；不返回合同正文、用户身份或模型凭据。`workers:status` 为受控命令行等价入口。实例数是正在持有名额的实例数，不是所有空闲进程数。历史失败指标只统计每份合同当前任务。

```sh
npm test
npm run typecheck
npm run typecheck:cloud
npm run build
npm run build
```

本轮按用户要求停止大批量并发验证，不提供“100 用户实测通过”的结论。保留调度、扩缩策略、共享会话和批量进度隔离的回归测试；最终变更仅做必要编译检查。

上线前仍需在目标服务器、真实模型账号上测延迟分位数、成功率、费用、内存和 CPU、数据库连接与 S3 网络；按结果设置实际总并发。PostgreSQL 默认每进程 10 个连接，网页、监督进程和每个后台进程都使用自己的连接池，扩容时必须计算合计连接数。增加执行名额不是增加 CPU 核心数，文档导出等 CPU 工作仍需要足够主机资源。
