# 小微企业合同 Agent 实测：2026-09-22

本文件保留修复前的原始审计。后续实施及复测见 [小微企业对话与事实处理升级](SMALL-BUSINESS-INTERVIEW-UPGRADE-2026-09-22.md)。

结论：目前还不能稳定达到“用户讲生意，只问重要缺口，生成合同交律师”的目标。模型经常已经理解了交易，但事实校验、追问判定和默认建议之间存在冲突，仍会让用户重复回答或卡在起草前。

## 测试范围与证据

- 本地完整 Pi SDK，实际调用 `deepseek-flash`，Thinking `high`。
- 20 个原有回归场景，加 8 个新增口语场景；覆盖采购、软件、保洁、装修、视频、租赁、保密、多方、无偿及互换交易，包含改价、撤回付款和金额矛盾。
- 原有场景：`.data/qa/intake-v4-1790046702880`；新增场景：`.data/qa/intake-v4-1790046764797`。各场景 JSON 保存实际回复和最终交易状态。
- 汇总：`.data/qa/small-business-audit-2026-09-22.json`。保留原始评分，没有覆写成新的“通过率”。
- 每个场景只采样一次；并发调用会影响延迟。本轮不是线上验收，也没有真人律师审查、法律效力结论或 Word 视觉排版验收。

## 主要发现

### 1. 已理解的金额被校验器错误拦截（最高优先级）

8 个新增口语场景中，5 个没有预设金额矛盾的场景仍收到“请明确一个合同总价，使用‘金额＋元’，费用明细另行说明”。另一个故意有金额矛盾的场景也只得到这一格式提示，没有真正指出算术矛盾。

实例如下：

| 用户原话 | 实际结果 |
| --- | --- |
| 总共1800块含税 | 回复先复述“1800元含税”，随后又要求提供总价 |
| 一个月1200，月底付 | 回复理解月费，校验仍要求合同总价 |
| 总共3万 | 回复理解3万元，校验仍要求重填 |
| 价格改成4000 | 记住新价与两次各2000，仍卡在金额格式 |
| 互不收钱（原回归场景） | 被当成缺少数值总价 |

根因在 `src/lib/contract-library/fact-checks.ts`：金额解析依赖“元/万元”格式；无偿表达仅覆盖少数固定词；周期价格只对少数合同族生效。另有一条软件场景中，同一“80000元”在原文证据里出现两次，校验按出现次数当成多个金额，错误要求一个总价。

`src/server/ai.ts` 把多个原文证据拼进 `facts.value`，随后数值检查直接解析这个展示文本。事实值、证据与计价方式没有充分分离。金额格式不是应该转嫁给用户的商业问题。

### 2. 仍会重复问已明确的信息

`price-correction` 第一轮已经给出 2026 年 10 月 1 日至 31 日，Agent 先复述这一工期，再问“准备什么时候开始、什么时候交付？”

运行日志同时记录 `intake_fact_rejected`：`field=term, located=false, numbersSupported=true`。代码要求证据逐字定位；普通专项场景中失败后会丢弃该字段，再由缺项检查追问用户。应先在系统内部修复证据引用，而不是让用户再次给出同一事实。该案例第二轮恢复工期，旧评测只检查最终状态，因此漏掉了第一轮重复问。

### 3. “重要缺口”与“可按通用规则处理”没有稳定区分

纸杯采购已说明数量、规格、图案、价格、交期、运费、付款节点及“检查数量、图案、漏水”，仍新增验收期限、付款期限、图样提交时间、不合格处理等确认项。独立 HTTP 测试里还生成了“要不要约定逾期违约金标准”的问题，并在回复里询问发票种类。

`src/lib/transaction-state.ts` 会把模型标为 `missing` 的业务字段全部作为阻断项，没有独立的重要性判定；法律问题过滤依赖字段名称，`nonconformityRemedy` 等自定义名称能携带违约金问题。限制最多三个问题，只限制了数量，并不保证这些问题都必要；一个问题内也可能塞进多个决定。

装修材料由谁采购确实影响费用和义务，应该问。普通补救措辞、法律适用、发票法律要求等不应一律拉回用户确认。

### 4. “常见建议”有时改变已明确约定

- 保洁：用户说“月底付”，建议变成“月底后3日内支付”。
- 纸杯、保洁、软件三条场景的建议加入“逾期未提出异议视为验收合格/服务完成”等安排。
- 视频及 Logo 建议额外涉及服务方展示作品的权利，超出原先简单的交付要求。

这些目前是**待确认建议**，不是已经写入 Word 的已确认条款。但它们不能当作无关紧要的默认细节。默认规则应保留已知事实，不自行扩大授权、转移风险或更改付款节点。

Skill 已要求仅对重要缺口追问，并保留已知限制；问题并非完全没有提示词，而是运行时没有可靠落实，建议环节也缺乏与既有事实、默认规则的一致性检查。

### 5. 真实矛盾没有用日常语言说清楚

用户说“50把椅子，每把100块，一共3000块”，Agent 先照抄矛盾数字，再报总价格式错误。更合适的唯一问题是：

> 50把、每把100元算下来是5000元。你说总共3000元，是有优惠吗？

原有使用“元”的 10 台 × 1000 元与总价 8000 元案例能正确识别矛盾，说明同一个业务问题仍受用户措辞影响。

### 6. 回复长度和等待时间仍影响体验

多条回复先大段重复双方、金额、工期、范围，再给问题或展示同样的交易摘要。软件第三轮信息已齐，回复仍列出长摘要并讲到法律适用等专业默认值。

28 个场景的首段可见回复时间中位数约 13.3 秒，最慢约 60.3 秒；这不是每轮延迟统计，也不是“全程没有界面反馈”。独立纸杯测试实际接收到了“正在理解交易 → 正在载入通用合同规则 → 正在核对本阶段结果”以及 7 个预览增量，说明本地后端与流式事件链路确实连接了。未做浏览器渲染、滚动流畅度或线上版本测试。

### 7. 旧自动评分明显过宽

原评分显示 20/20 和 8/8，但它只核对选定的最终字段、缺项、参与方或关键文本；没有普遍拒绝意外 `conflicts`，没有检查每轮重复问，也没有要求完整交易能进入起草。

28 个场景中，7 个未预设金额矛盾的场景最终出现了错误的总价冲突；不能把“28/28”当成可用性通过率。含故意缺项的场景本来就应追问，也不能反过来把全部尚未可起草的场景都计为失败。

## 完整交付流程

纸杯原始口语输入通过本地 HTTP、独立 PostgreSQL schema、真实模型和后台任务执行。文件存储使用本地 S3 协议测试服务，不涉及公网或真实律师。

结果：失败于起草前，`missing=[paymentTimeline, acceptance, nonconformityRemedy]`，另有错误的总价冲突。没有生成 Word，也没有提交审核；证据目录 `.data/qa/qa_small_business_1790046858016`。测试没有替用户补答来掩盖问题。

另行使用独立保密协议案例测试完整链路，成功完成：事实整理（没有新增追问）→确认摘要→后台起草与核对→生成并下载真实 DOCX→提交指定版本→模拟律师账号读取同一文件。总耗时约 63.3 秒；28 个预览增量，含起草、核对及保存 Word 的阶段事件。证据目录 `.data/qa/qa_small_business_1790047108914`，结果见 `result.json`，实际文件为该测试脚本固定命名的 `purchase.docx`（文档内容及标题为《保密协议》）。已抽取正文核对包含双方、保密范围、用途、两年期限和签署页；没有真人法律评审或视觉排版验收。

两次 HTTP 测试均使用隔离的数据库 schema 和合成账号，结束后已清理；未给真实律师发送任何信息。本轮增加测试用例和验收脚本，未修改生产业务逻辑，未部署；相关 TypeScript 检查通过。

## 建议的最小改进顺序

1. 先修事实处理：保存用户证据，同时提取规范金额、计价方式、付款事件；同一金额多处引用不重复计数。引用失败先内部修复，不直接追问。
2. 追问只针对会改变双方主要义务的未定事实或真实冲突；已明确、可依默认法律规则起草的内容不阻断。保留“尚未商定”而不是编造共识。
3. “按常见方式处理”分两类：专业措辞和普通法律补救直接起草并供律师审核；新增价格、实质授权、默示验收、商业责任分配等不伪装成小事，必要时只问一条简短问题。
4. 回复只接住本轮新增内容，加 1—3 个重要问题；完整事实放摘要，不在对话里反复复述。
5. 评测检查每一轮和整条交付流程，分别记录重复问题、无关问题、事实改变、实际 Word 生成与审核入口；真人律师修改量需要后续独立评审。

这些优先是事实与追问机制的修正，不需要再堆多个 Agent 或更大的知识库。当前证据不足以把问题归因于 Flash 模型或 Pi SDK 本身。
