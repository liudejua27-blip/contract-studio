# 合同 Agent 流式界面升级方案

2026-09-21 · 方案阶段。依据当前本地代码与官方组件文档；未实施、未部署，未对线上浏览器掉帧或网络耗时作性能实测。

## 目标与选型

用户发送后立即得到反馈，回答持续出现在原位置，生成合同时能看到条款逐步形成；等待期间可阅读、滚动、准备下一条消息或停止。最终下载和律师审核仍绑定实际保存的 Word。

复用现有 `@assistant-ui/react`、Pi SDK、SSE 和文档服务。采用一个聊天运行时，通过自定义适配器接入 Pi 的公开事件。保留网站中文和绿色识别色，借鉴 GPT 式的简洁会话、渐进输出和文档工作区；不声称复制 ChatGPT 内部实现。

| 组件方向 | 选择 |
| --- | --- |
| assistant-ui | 主组件库：会话、消息、输入、停止、回到底部、可操作内容块；项目已安装，优先适配现有版本 |
| OpenAI ChatKit | 参考聊天、工具状态、卡片和动作设计；本轮不迁移会话协议或新增后端运行时 |
| Vercel AI Elements | 参考文档与任务卡样式，不整包安装；其推荐栈引入 AI SDK、shadcn 和 Tailwind，超出本轮必要范围 |
| Streamdown | 流式 Markdown 的候选渲染器；先对比 assistant-ui 配套方案，只选一个，通过中文长文本与未闭合语法测试后使用 |

现有依赖为 assistant-ui 0.11 系列，官网新接口不能直接假定兼容。实施先核对已安装类型；只为必需能力做受控升级，不顺带升级整个前端栈。

## 本地代码中观察到的问题

| 证据位置 | 当前行为 | 影响及判断边界 |
| --- | --- | --- |
| `src/components/Chat.tsx` | runtime 只接收持久化消息；预览另放在会话视口外 | 正式回答与正在生成的内容分离 |
| `src/components/Studio.tsx` | 运行任务期间轮询间隔 2,500ms，由浏览器触发下一阶段 | 阶段之间可能等待下一轮轮询；页面离开不等于已有后台执行器 |
| 同上 | 每次启动阶段清空 text，结束后删除临时 stream 状态 | 已显示内容可能消失、闪动或退回骨架屏 |
| 同上 | 每次 preview 更新页面顶层 state | 可能扩大重绘范围；是否实际掉帧须用 Profiler 验证 |
| `src/lib/agent-stream.ts` | 从累计 JSON 正则抽取 reply/title/content，截取前 24,000 字符 | 回复字段未到达时无文字；长文本超过上限后预览停止增长；字段名筛选缺少结构路径约束 |
| `src/server/agent/model-stream.ts` | 已有约 80ms 的输出节流，但每次发送累计全文 | 并非完全没有流式；仍有重复解析、传输全文的开销 |
| `src/server/agent/transport.ts` | 模型 SSE 被读取，公开预览走旁路；Pi 消息 start/done 在完整响应后送出 | 仅订阅 Pi 最终事件或换 UI 库不能获得连续正文 |
| `src/components/AgentProgress.tsx` 与样式 | 大进度卡、卡内滚动、预览再次滚动，聊天另有滚动区域 | 阅读空间被挤占，滚动路径复杂；当前固定步骤也不完全匹配纯问答轮次 |
| `src/components/Chat.tsx` | busy 时整个输入框 disabled | 用户等待期间无法准备补充内容 |

`DocumentPreview` 的 Word 加载依赖 version ID，并没有在每个字到达时重新解析 Word。因此不把 DOCX 反复解析当成本轮已证实的卡顿原因。

## 交互布局

普通交流保持单栏：消息正文最大宽度约 760px，用户消息用浅色圆角块，助手用留白和清晰段落。输入框固定在会话底部，不随进度卡高度跳动。

开始起草后，桌面打开右侧文档面板，聊天约占 40%、文档约占 60%，允许收起文档。窄屏不强行双栏；显示“对话 / 合同”切换和文档生成状态。每个面板一个主要滚动区域，去掉进度卡内的小型滚动预览。

```text
最近合同      对话                            合同初稿 · 生成中
              你：按这些条件生成合同          软件开发服务合同

              助手：                         一、项目内容
              正在起草条款 · 18 秒 ▾         ……正在持续补充正文……
              已整理双方、费用及交付安排。
              [合同初稿 · 查看]              二、交付与验收
                                             ……
              ┌ 可以提前输入补充内容… ┐
              └──────────────── [停止]┘      尚未完成核对
```

示意中的说明只在有真实事实/阶段依据时显示，不让定时动画伪装成 Agent 已完成工作。

## 六种消息内容

1. **普通回复**：同一消息 ID 持续追加正文，支持段落、列表和表格；禁止全文返回后再用定时器逐字播放。
2. **工作状态**：回复上方一行“正在核对交易 / 正在查阅相关规则 / 正在起草条款 / 正在核对约定 / 正在保存 Word”。展开可看已经发生的步骤，完成后收起。纯问答不显示完整起草步骤条。
3. **交易摘要**：紧凑、默认折叠；必要时提供“确认并生成”，不长期占据半屏。
4. **商业建议**：一项具体建议搭配“采用 / 修改”，与原话和已确认事实分开。
5. **合同卡片**：起草中可打开实时预览；保存成功后显示名称、版本、AI 初稿状态，以及“下载 Word / 提交律师审核”。按钮使用服务端权限和真实文件凭据。
6. **中断提示**：在原消息保留部分预览和“未完成”状态，提供重试；不清空对话，不把失败结果标为完成。

工作状态仅展示公开执行摘要；不展示私有推理、原始工具参数、内部路径或未授权的信息。

## 真正流式的连接方式

```text
模型增量与 Pi 工具/任务状态
  → 服务端筛选并规范化公开事件
  → SSE
  → 会话专用 store / reducer
  → assistant-ui 当前消息 + 文档块
```

同一 job 在理解、生成、核对、导出之间保留当前展示对象。有效结果到达后用服务器消息和版本对齐，不新增一条重复回复。阶段完成立即推进允许的下一阶段，轮询只用于恢复和兜底；保持现有请求幂等与任务租约，不能多个浏览器同时重复执行。

建议事件包含 `contractId / jobId / attemptId / seq / type`，文本块额外使用 `messageId / blockId`。这些标识由服务端建立并校验权限，不能相信浏览器提交的跨合同标识。

| 公开事件 | 前端操作 |
| --- | --- |
| run.started / phase.changed | 创建或更新同一运行记录 |
| message.delta | 向该回复追加用户可读文字 |
| document.block.delta | 更新对应标题、条款或附件，不反复替换整份文档 |
| tool.started / tool.finished | 更新简短工作状态；只传白名单摘要 |
| preview.replaced | 重试或修复生成新候选时切换候选版本，禁止与旧正文拼接 |
| artifact.ready | 接收真实文档版本，开启下载/送审 |
| run.failed / run.cancelled / run.completed | 完成当前状态，保留已有内容 |
| snapshot | 页面重进或事件缺口时恢复当前状态 |

既有 JSON 工具结果暂时保留；服务端使用能处理分片字符串的路径感知解析，公开字段限定为 `reply`、合同标题、正文及附件文本等具体路径，不能只按任意同名 `content` 提取。结构化最终结果仍须完整校验才能进入保存。模型若一直先输出非展示字段，记录首字延迟并调整输出顺序/协议，不用假文字掩盖等待。

去重按 attempt 和 seq；缺号时获取服务端快照，不能声称已有无限事件回放。缓存会话的部分预览可用于当前页面连续展示，刷新恢复范围以实际持久化快照为准。完整 token 日志和独立后台队列不作为本轮前提。

## 消除卡顿和跳动

- 将高频流式 state 从 `Studio` 移到会话专用 store，仅当前消息/条款订阅增量。已完成消息保持稳定引用；会话目录、律师表单和已保存 Word 不跟着正文增量更新。
- 用短缓冲合并增量，在约 30–80ms 的可调窗口内刷新，不对每个字符触发整页状态更新。最终一批、错误和完成事件立即 flush；依据实测调整，不承诺模型固定首字速度。
- 已完成段落缓存，仅解析正在增长的末尾块。长合同按条款增量更新；去掉静默的 24,000 字符截断。若达到服务端明确输出上限，显示截断/恢复状态，不继续假装生成。
- 用户在底部时跟随新内容；用户向上阅读立即停止自动跟随，显示“回到最新”。阶段切换、重试和文档开启都不强行夺取滚动位置。
- 生成阶段用轻量 HTML 文本预览；Word 保存成功后再加载实际 DOCX，切换时保留可见内容，避免空白闪屏。明确两者分别是实时草稿与已保存文件。
- 输入框可以继续编辑草稿，发送按钮在运行时变成停止。本轮先不提供并行发送队列；停止被服务器确认后才能发送修改，避免模型仍在生成旧条件。
- 停止操作调用服务端 cancel；仅断开 SSE 不算停止。切换会话只解绑显示/连接，不自动取消业务任务。迟到事件不得串到另一个合同。
- 若模型暂时没有公开正文，显示真实阶段、已用时间和停止入口；心跳只证明连接存活，不表示业务进展。失败保留内容并区分重新连接与重新执行。
- 支持中文输入法组合输入、键盘操作、移动端软键盘和减少动画偏好；辅助阅读器仅播报状态变化，不逐字符朗读。

## 实施范围

第一批完成真正的会话内流式输出、独立流式状态、阶段连续性、滚动及停止/重试。涉及 `Chat.tsx`、`Studio.tsx`、`stream-job.ts`、公开事件和服务端投影适配。保留底层 Pi 与既有事实校验。

第二批完成简洁视觉、内联卡片和合同侧面板，复用 `AgentProgress`、`IntakePanel`、`DocumentPreview` 的业务逻辑；新增组件可命名为 `AgentActivity`、`StreamingDocument`、`ContractArtifactCard`。不为了界面升级改变用户确认、律师送审和文件权限。

第三批进行真实浏览器性能与异常验收。使用本地合成交易，记录模型、SSE、渲染三个时间点，先确认瓶颈再进一步优化。现有线上服务是否包含当前本地代码需部署前另行确认；本轮不部署。

## 验收目标（待实施测量）

| 场景 | 判定 |
| --- | --- |
| 点击发送 | 正常本地条件下 100ms 内出现用户消息和发送状态；网络失败保留可重试消息 |
| 正文持续到达 | SSE 增量收到至界面显示 P95 ≤ 200ms；模型首字耗时单独记录 |
| 超过 24,000 字符的长合同 | 末尾仍持续变化，正文完整，不靠裁剪掩盖性能问题 |
| 100 条历史消息加持续增量 | 输入和滚动可用；Profiler 验证没有由每批增量引起的整个页面重绘；记录超过 50ms 的长任务并定位 |
| 阶段切换与修复 | 已显示内容不清空；新候选明确替换旧候选，不混合文本 |
| 上滑、移动端、切换会话 | 不强拉到底、不遮挡输入、不出现跨合同消息 |
| 丢包/断网/刷新/重复事件 | 恢复已保存状态，正确标注未完成，无重复合同或虚假下载 |
| 停止与迟到事件 | 服务端确认取消后停止应用旧任务增量，能继续输入新要求 |
| Word 生成成功 | 卡片下载的是该版本的真实 DOCX，律师接收同一版本 |

这些是验收目标，不是已实现性能。组件升级主要改善可见进展和渲染，不会自动缩短模型推理或后台文件保存耗时。
